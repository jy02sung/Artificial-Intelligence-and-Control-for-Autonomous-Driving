# 기존 학습 데이터와 추가 권장 데이터

작성일: 2026-10-27  
코드 확인 기준: `ca9fd4c421c72b7c457bfb70f7f36e98537bd5f4`  
**도로 및 프로젝트 주제: 미정**

이 문서는 현재 구현된 데이터와 향후 추가를 제안하는 데이터를 구분하기 위한 팀 논의 자료입니다. 특정 도로를 채택하거나 관측·보상·모델 구조 변경을 확정한 문서가 아닙니다. 이번 작업은 문서화만 수행하며 학습 코드는 변경하지 않습니다.

## 1. 먼저 구분할 세 가지

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 모델 입력(관측) | 정책이 행동을 결정할 때 실제로 받는 정보 | 내 속도, 앞차 거리 |
| 저장 데이터 | 수집 파일에 기록되는 입력·행동·결과·부가 정보 | 보상, 종료 여부, 감지 차량 좌표 |
| 주행 시나리오 | 모델이 경험하도록 환경에서 생성하는 상황 | 교통량, 합류 간격, 버스 정차 |

**파일에 정보를 저장하는 것만으로 모델 입력에 추가되지는 않습니다.** 정책이 활용할 정보는 환경의 관측 생성과 모델 입력에 연결해야 합니다. 학습률·배치 크기 등 하이퍼파라미터와 보상 계수도 관측 데이터와는 별도 설정입니다.

## 2. 현재 모델 입력: 31차원

기본 환경은 12km 편도 3차로 고속도로입니다. 관측은 현재 차로와 좌우 두 차로씩 총 5개 차로 위치를 대상으로 하며 기본 감지 거리는 50m입니다. 존재하지 않는 차로도 정해진 값으로 채워 입력 크기를 유지합니다.

| 기존 정보 | 인덱스 / 개수 | 의미 |
| --- | --- | --- |
| 내 속도 | 0 / 1개 | 제한속도로 정규화한 자차 속도 |
| 차로별 앞차 거리·상대속도, 뒤차 거리·상대속도 | 1–20 / 20개 | 차로당 4개 값 × 5개 차로 |
| 차로별 연결성 | 21–25 / 5개 | 차로 존재 여부, 관측 범위 내 차로 끝·연결 여부 |
| 차로별 전방 차량 밀도 | 26–30 / 5개 | 관측 범위 내 전방 차량 수를 수용 대수로 정규화 |
| **합계** | **31개** | **같은 방향 차량의 추종과 차선 변경 중심** |

출력 행동은 가감속과 차선 변경의 2개 성분입니다. 현재 PPO는 가감속 연속 출력과 차선 선택 이산 출력을 결합한 hybrid 정책을 사용합니다.

현재 명시적 입력에 없는 정보:

- 목표 진행 방향·출구와 경로상 남은 거리
- 목표 경로로 이어지는 차로인지 여부
- 신호등 상태와 진입 우선순위
- 다른 진입로에서 접근하는 차량의 움직임을 체계적으로 표현한 정보
- 최근 여러 시점의 관측 이력

### 교차로로 확장할 때의 기존 코드 한계

일부 관측 처리는 직선 도로에 맞춰져 있습니다. 차로 밀도는 다음 차로를 볼 때 첫 번째 연결을 사용하며, 교차로 내부에서 일부 항목은 중립값 또는 빈 목록으로 처리됩니다. 감지 차량 부가 기록도 현재 edge의 차로를 중심으로 수집합니다. 따라서 도로 XML만 바꾸거나 입력 개수만 늘려서는 충분하지 않고, **교차로·연결 구간에서 관련 차량을 찾는 로직**도 검토해야 합니다.

근거: [관측·행동 설정](../env/mdp_config.py), [실제 환경 구현](../env/sumo_env.py), [도로 설정](../env/road_config.py), [PPO 학습 설정](../train.py).

## 3. 기존 샘플 파일에 저장된 데이터

`data/dataset.npz`를 직접 확인한 결과 **4,941개 전이 기록**이 있습니다. 전이는 행동 전 관측, 행동, 보상, 행동 후 관측 등을 묶은 한 스텝의 기록입니다. 4,941개는 차량 수나 에피소드 수가 아닙니다.

| 키 | 실제 배열 크기 | 내용 및 현재 용도 |
| --- | --- | --- |
| `observation` | `(4941, 31)` | 행동 전 관측, 정책 입력 |
| `action_raw` | `(4941, 2)` | 가감속·차선 변경 행동, BC 학습 목표 |
| `next_observation` | `(4941, 31)` | 행동 후 관측 |
| `reward` | `(4941,)` | 스텝별 보상 |
| `terminated` | `(4941,)` | 환경 종료 여부 |
| `truncated` | `(4941,)` | 시간 제한 등으로 중단됐는지 여부 |
| `episode` | `(4941,)` | 에피소드 번호 |
| `t` | `(4941,)` | 에피소드 내 스텝 |
| `lane_change` | `(4941,)` | 양자화한 차선 변경 명령, -1/0/+1 |
| `detected_xy` | `(12300, 2)` | 감지 차량의 절대 좌표를 기록별로 이어 붙인 배열 |
| `detected_offsets` | `(4942,)` | 각 전이의 좌표 구간을 찾는 시작·끝 위치 |

`detected_xy`의 12,300개는 **서로 다른 차량 수가 아니라 시점별 감지 기록 수**입니다. 이 좌표는 현재 31차원 정책 입력에 포함되지 않습니다.

`lane_change`는 명령이며 실제 차선 변경 성공을 보장하지 않습니다. 현재 수집 코드의 JSONL에는 `lane_change_applied`, 변경 전후 차로, 충돌·도착 이벤트도 기록됩니다. NPZ에 이 상세 정보가 모두 들어 있는 것은 아닙니다.

현재 수집기는 NPZ와 압축 JSONL(`.jsonl.gz`)을 생성합니다. JSONL에는 SUMO 내부 상태(`state`)와 감지 차량 상세 정보도 기록하지만, 이것이 모두 정책 입력이라는 뜻은 아닙니다. 중간 레코드에서 생략된 다음 관측·상태는 `iter_transitions()`로 복원할 수 있습니다.

기존 샘플의 관측·행동 크기는 현재 환경과 일치합니다. 다만 **데이터를 만든 정책의 운전 품질과 시나리오 분포는 별도 평가가 필요**하며, 크기가 맞는다는 이유로 전문가 시범 데이터라고 간주하지 않습니다.

근거: [샘플 데이터](../data/dataset.npz), [데이터 수집기](../collect_pomdp_data.py), [BC 학습기](../train_bc.py).

## 4. 추가하면 좋은 모델 입력 — 제안

최종 항목과 입력 차원은 도로·학습 목표를 정한 후 결정합니다. 아래 우선순위는 교차로·합류·진출 상황을 다루는 경우를 가정한 제안입니다.

| 추가 정보 | 기존 정보와의 차이 | 학습에 필요한 이유 | 제안 우선순위 |
| --- | --- | --- | --- |
| 목표 진행 방향·출구 | 현재 목적지가 명시적으로 없음 | 직진·회전·진출별 행동 구분 | 높음 |
| 목표 경로로 연결되는 차로 여부 | 기존 연결성은 목표 경로 적합성까지 보장하지 않음 | 잘못된 차로 진입·출구 놓침 방지 | 높음 |
| 합류점·정지선·출구까지 거리 | 현재 이런 기준점과의 거리가 없음 | 감속·차선 변경 시점 판단 | 높음 |
| 다른 진입로 차량의 상대 위치·속도·진행 방향 | 기존 관측은 같은 방향 차로 중심 | 옆에서 합류하거나 진행 경로를 가로지르는 차량 파악 | 높음 |
| 신호 상태·통행 우선순위 | 현재 명시적 입력 없음 | 진입·대기 판단 | 해당 도로에 필요할 때 높음 |
| 최근 몇 스텝의 관측 | 현재 정책은 한 시점의 관측 중심 | 상대 가감속·접근 추세 파악 | 다음 단계 |
| 차량 길이·차종 | 현재 명시적 입력 없음 | 버스·승용차의 공간 점유 차이 반영 | 대형 차량 실험 시 |
| 위험 여유시간 등 파생 지표 | 기존 거리·속도에서 추가 계산 | 빠르게 접근하는 위험 구분 | 보조 |

추가 입력 설계 시 고려사항:

- 위치·속도는 가능하면 자차 기준 상대값으로 표현하고 정규화합니다.
- 주변 차량 수가 달라지므로 선택 기준, 최대 개수, 빈 항목 마스크를 정합니다.
- 신호 잔여시간이나 다른 차량의 미래 경로는 실제로 알 수 있다고 가정하는지 명시합니다. SUMO에서 조회 가능하다는 이유만으로 정책 입력으로 사용하지 않습니다.
- 서로 다른 방향의 차량에는 단순 앞뒤 거리 대신 경로가 만나는 지점까지의 거리·예상 도착시간 등 적합한 표현을 검토합니다. 위험 지표 계산 방식은 도로 선정 후 정의합니다.
- 신호가 없으면 신호 입력을 억지로 추가하지 않습니다. 필요 없는 정보를 무조건 늘리는 것이 목표는 아닙니다.

## 5. 추가하면 좋은 주행 상황 — 제안

| 경험시킬 상황 | 기대하는 판단 |
| --- | --- |
| 교통량 적음·보통·많음 | 특정 혼잡도에만 적응하지 않기 |
| 합류 간격 충분·애매·부족 | 진입할 때와 기다릴 때 구분 |
| 주변 차량의 속도·가감속 차이 | 상대 움직임에 맞춘 속도 조절 |
| 목표 출구까지 여유가 있는 상황과 가까워진 상황 | 미리 적절한 차로 선택 |
| 버스 정차·재출발 | 큰 차량의 진출입에 대응 |
| 출발 시점·교통 생성 시드 변화 | 특정 배치를 외우지 않기 |

한 번에 모두 추가하지 않고, 기본 상황에서 동작을 확인한 뒤 혼잡도와 상호작용을 늘리는 방식을 제안합니다. 학습용과 평가용 에피소드·시드를 구분하고, BC 데이터는 같은 에피소드의 인접 스텝이 양쪽에 섞이지 않도록 분할합니다.

## 6. PPO와 BC에서 바꿔야 하는 것

| 구분 | 현재 데이터 사용 방식 | 입력·상황을 추가할 때 |
| --- | --- | --- |
| PPO 강화학습 | `train.py`가 SUMO에서 새 경험을 수집해 학습. 기존 NPZ를 읽어 학습하는 흐름이 아님 | 관측 생성, 도로·교통 시나리오, 필요 시 행동·보상·종료 조건을 수정하고 새 환경에서 학습 |
| BC 모방학습 | `train_bc.py`가 저장된 관측과 행동의 쌍을 학습 | 새 관측 정의에 맞는 시범 데이터를 수집하고 입력 구조를 맞춰 학습 |

입력 차원이나 의미가 달라지면 기존 모델을 그대로 사용할 수 있다고 가정하지 않습니다. 기존 31차원 데이터에 새 항목을 임의의 값으로 채워 넣기보다는 새 환경에서 재수집하는 것을 기본으로 검토합니다. 임의 정책으로 수집한 데이터는 파이프라인 확인에는 쓸 수 있지만 좋은 BC 운전 정책의 근거가 되지는 않습니다.

## 7. 재현성과 평가를 위해 함께 남길 기록 — 제안

- 관측 스키마 버전, 코드 커밋, 도로 버전, SUMO 버전
- 교통량·차종 구성·시드·출발 및 목표 경로
- 데이터 생성 정책과 모델 버전, 하이퍼파라미터·보상 설정
- 목표 경로 완주율, 충돌률, 시간 초과율, 통과 시간
- 필요 시 신호 위반, 출구 놓침, 급감속, 안전 게이트 개입 횟수

현재 학습 스크립트는 일부 설정 파일을 run 폴더에 복사합니다. 위 목록 전체가 이미 자동 기록되는 것은 아닙니다. 안전 게이트가 행동을 차단하는 경우 정책 성능과 안전장치 효과를 구분해 해석합니다.

## 8. 팀에서 결정할 항목

1. 실제 도로와 재현 범위, 자율주행 차량의 주행 과제
2. 고정할 출발·도착 경로와 변화시킬 교통 조건
3. 모델이 관측할 수 있다고 가정하는 정보
4. 최소 추가 입력과 보상·성공·실패 정의
5. BC 시범 정책의 출처·품질 기준 및 PPO 비교 조건

현재 권장 출발점은 기존 관측이 새 도로에서도 정확한지 확인한 뒤, **목표 경로·충돌 가능 접근 차량·통행 조건** 중 해당 과제에 필요한 정보부터 추가하는 것입니다. 구체적인 도로와 최종 설계는 팀 논의 후 확정합니다.
