# 1. 중간발표

중간발표에서는 각 팀이 선정한 도로와 프로젝트 방향 짧게 공유

> **팀당 발표 시간은 최대 3분**
> 시간 엄수

## 1.1 발표 방식

- 발표 순서는 **팀 번호 순**
- 발표자는 **1명 / 여러 명 가능**
  - 팀에서 자유롭게 결정

## 1.2 평가 방식

중간발표에서는 **학생 상호평가를 진행하지 않음**

```text
학생 평가 X

교수 / 조교 평가 O
```

중간발표 목적:

> **현재 프로젝트 방향에 문제가 없는지 확인**

특히 도로 선정, 차량 interaction, 데이터 구성 등이 프로젝트 목적과 맞는지 확인할 예정

---

## 1.3 중간발표에 포함해야 할 내용

### 1) 어떤 지역의 실제 도로를 선정했는가?

예:

```text
서울 광화문
수원 팔달문
강남역 인근
부산 해운대
성균관대학교 주변
```

지도 또는 실제 도로 이미지를 함께 보여주는 것 권장

### 2) 해당 도로의 구조적 특징은 무엇인가?

예:
```text
- 삼거리
- 사거리
- 오거리
- 회전교차로
- 합류 구간
- 분기 구간
- 다중 차선
- 차로 감소
- 비정형 교차로
```

단순히 "이 지역을 선택했다"가 아니라

> **자율주행 환경으로 구현했을 때 어떤 구조적 특징이 있는가?**

를 설명

### 3) 이 도로가 왜 흥미로운가?

선택한 지역이 왜 프로젝트에 적합한지 설명

예:

```text
여러 방향에서 차량이 동시에 진입
    ↓
차량 간 상호작용 증가
    ↓
속도 조절 / 양보 / 합류 / 차선 변경 필요
```

유명한 장소를 선택했다는 것만으로는 충분하지 않음

> **자율주행 의사결정 문제로서 왜 의미 있는 도로인지 설득하는 것**

이 중요

### 4) 어떤 차량 interaction이 발생하는가?

도로 구조에서 발생할 수 있는 차량 간 상호작용 설명

예:
```text
- 직진 차량과 좌회전 차량의 interaction
- 합류 차량과 본선 차량의 interaction
- 회전교차로 진입 차량과 내부 차량의 interaction
- 차로 감소 구간에서의 양보
- 느린 차량 추월
- 다중 차선에서의 차선 변경
```

즉,

```text
도로 구조
    ↓
차량 interaction
    ↓
AV가 해야 하는 의사결정
```

이 연결되어야 함

### 5) 수집할 데이터 컬럼

프로젝트에서 수집할 데이터의 형태 소개

예:

```text
Episode
Step
Ego position
Ego speed
Ego lane
Surrounding vehicle information
Action
Reward
Next State
Done
```

> **State (절대적인 정보) 관련 데이터 컬럼은 반드시 포함**

### 6) 팀 이름 및 역할 분담

팀 정보와 역할 분담 **1페이지**로 정리

역할 분담 예:

| 팀원 | 역할 |
|---|---|
| 팀원 A | SUMO 도로 환경 구축 |
| 팀원 B | 일반 차량 / Traffic 구성 |
| 팀원 C | AV 학습 / 평가 |
| 팀원 D | 데이터 수집 / 프로젝트 페이지 |

역할이 완전히 분리될 필요는 없으나,

> **누가 어떤 부분을 중심적으로 담당하는지 확인할 수 있도록 정리**

## 1.4 중간발표 슬라이드 구성 예시 (참고용이며, 자유롭게 구성 가능)

3분 발표이므로 슬라이드를 너무 많이 만들 필요 없음

```text
Slide 1
팀 이름 / 팀원 / 역할 분담

Slide 2
선정 지역 + 실제 도로 이미지

Slide 3
도로 구조적 특징 + SUMO 구현 계획

Slide 4
예상 차량 interaction + 자율주행 문제

Slide 5
수집 데이터 컬럼
```

> **3분 안에 핵심만 전달하는 것이 중요**

## 2.1 최종발표에 포함할 내용

최종발표에서는 단순히 학습 결과 숫자만 보여주는 것이 아니라

> **도로 구축 → 차량 interaction → AV 학습 → 평가 → 데이터 수집**

전체 과정을 보여주어야 함

중간 발표 내용을 포함하여 최소한 다음 내용을 포함하는 것을 권장

```text
- 선정한 실제 도로와 구현한 SUMO 환경
- 도로 구조적 특징
- 일반 차량 구성
- AV Observation / Action / Reward
- 학습 방법
- 정량적 주행 성능
- Collision Rate
- 목적지 완주 여부
- 실제 주행 영상 (30초 이상)
- 수집 데이터 설명
- 프로젝트에서 발견한 문제와 해결 과정
```

### 실주행 영상

최종발표에는

> **30초 이상의 실제 주행 영상**

을 반드시 포함해야 함

영상에서는 다음이 드러나야 함

```text
도로 구조
일반 차량 움직임
AV 움직임
차량 interaction
목적지까지의 주행
```

## 2.2 최종 프로젝트 평가 요소

최종 프로젝트는 다음 기준을 만족해야 함

### 1) Collision Rate

기본 목표:

> **Collision Rate < 5%**


예:

```text
Evaluation 100 Episode
Collision 4 Episode

→ Collision Rate = 4%
```

### 2) 목적지 완주

자율주행 차량이

```text
Start
  ↓
주어진 도로 주행
  ↓
Goal
```

까지 **문제 없이 완주**

단순히 충돌하지 않는 것뿐만 아니라

- 비정상적으로 정지하지 않는가?
- 잘못된 Route로 빠지지 않는가?
- 특정 위치에서 무한정 대기하지 않는가?

등도 함께 확인 예정

### 3) 충분한 일반 차량 존재

자율주행 차량 혼자 주행하는 환경은 프로젝트 목표에 적합하지 않음

따라서 Evaluation 시점에

> **일반 차량이 일정 수 이상 존재하는 교통 환경**

을 구성

중요한 것은

```text
AV 혼자 주행
```

이 아니라

```text
여러 HV + AV
    ↓
의미 있는 interaction 발생
```

이 되어야 함

### 4) 도로 형태

도로 형태에는 별도의 제한을 두지 않음

```text
Open Road
Loop Road
Intersection
Roundabout
Merge / Diverge
```
신호등 추가 가능

모두 가능

## 2.3 프로젝트 평가 기준 요약

전체적인 환경 완성도와 프로젝트 수행 과정을 함께 평가 예정

| 평가 항목 | 평가 내용 |
|---|---|
| **도로 구조 구현** | 실제 도로의 특징이 자연스럽게 반영되었는가 |
| **도로 구조의 의미** | AV가 의사결정을 해야 하는 구조적 특징이 존재하는가 |
| **Vehicle Interaction** | 일반 차량과 AV 사이에 의미 있는 interaction이 발생하는가 |
| **Simulation 안정성** | 차량이 정상적으로 주행하며 비정상적인 정체 / Teleport / 오류가 없는가 |
| **AV 주행 성능** | Collision Rate, 완주 여부 등 기본 주행 성능을 만족하는가 |
| **Traffic 구성** | 충분한 수의 일반 차량이 존재하고 자연스럽게 움직이는가 |
| **Dataset 구축** | 데이터가 10^7개 이상이 올바르게 저장되는가 |
| **분석 및 설명** | 환경 설계 이유, 문제점, 해결 과정을 논리적으로 설명하는가 |
| **최종 결과물** | 프로젝트 페이지, 코드, 발표자료, 데이터 등을 요구된 형태로 제출했는가 |
| **동료 평가** | 다음의 [양식](https://docs.google.com/document/d/1czmE5ofrKckau2rMwK4-wXax-f5QrUia/edit?usp=sharing&ouid=107893289049883287038&rtpof=true&sd=true) 사용 예정 |


### 동료 평가 항목

- 다른 팀의 발표를 듣고 아래 항목을 중심으로 동료 평가 진행 예정
- 프로젝트 내용 90점과 발표 10점을 합산하여 총 100점으로 평가

| 평가 항목 | 평가 내용 |
|---|---|
| **도로 구조 설계 및 구현** | 실제 도로의 구조적 특징이 잘 반영되어 있고, 도로 선정 이유, 자율주행 문제로서 흥미로운 구조를 가지고 있는가 |
| **일반 차량 구성 및 차량 간 상호작용** | 일반 차량이 함께 주행하며, 일반 차량과 AV 사이에 합류, 양보, 차선 변경, 교차로 통과 등 의미 있는 interaction이 충분히 발생하는가 |
| **데이터 수집 항목의 설계 및 구성** | 수집한 데이터 항목별 의미/단위/저장 구조가 적절하고 각 항목의 필요성을 설명하며, 데이터 수집 규모, 조건을 잘 제시했는가 |
| **주행 결과 및 문제 해결 과정** | 주행 영상 및 정량적 결과를 제시하여 AV가 충돌이나 비정상적인 정지 없이 안정적으로 주행하고 목적지까지 완주하는가, 도로 구현, 차량 주행, 데이터 수집 과정에서 발생한 문제와 해결 방법을 구체적으로 설명했는가 |
| **발표자료·시간 준수·발표능력 및 준비력** | 발표를 충분히 준비하여 원활하게 발표를 진행하고, 프로젝트의 핵심 내용과 결과를 제한된 시간 안에 이해하기 쉽게 전달했는가 |

동료 평가에서는 단순히

```text
도로가 복잡하다
Collision Rate가 낮다
데이터가 많다
```

만을 기준으로 평가하지 않음

보다 중요하게 보는 것은

```text
왜 이 도로를 선택했는가?
        ↓
어떤 Vehicle Interaction이 발생하는가?
        ↓
AV가 해당 상황을 안정적으로 해결하는가?
        ↓
그 과정이 데이터에 잘 기록되어 있는가?
```

임

> **복잡한 도로보다, 프로젝트의 목적과 차량 interaction이 명확하게 드러나는 환경을 높게 평가**

### 동료 평가 시 참고

- 본인 팀을 제외한 다른 팀을 평가
- 발표 내용과 주행 영상, 제시된 결과를 기준으로 평가
- 단순한 선호도보다는 **프로젝트의 완성도와 자율주행 환경으로서의 의미**를 기준으로 평가
- 평가 결과는 최종 성적의 일부로 반영될 수 있음

## 2.4 최종 결과물

최종적으로 각 팀은 다음 결과물을 제출해야 함

- 해당 결과물(코드, 학습한 모델 파일, 데이터, 발표자료)은 아이캠퍼스 과제함 (추후 생성 예정)에 마감 기한까지 제출 필요
- 마감 기한 이후로는 결과물 받지 않을 예정
- 마감 기한 이후 최신화 불가, 평가는 아이캠퍼스에 제출한 파일로 진행 예정

### 1) 프로젝트 페이지

다른 사람이 프로젝트를 보고

```text
무엇을 만들었는지
어떤 도로인지
어떻게 실행하는지
어떤 결과가 나왔는지
```

이해할 수 있도록 구성

프로젝트 페이지에 아래의 예시 자료처럼 코드(깃허브) 링크, 발표자료(pdf) 접근 가능 링크, 데이터(허깅페이스) 링크를 달아서 접근 가능해야 함

- 예시 자료 1: <https://park-sangeun.github.io/Multi-Square/>
- 예시 자료 2: <https://9hyeon1225.github.io/van/>
- 예시 자료 3: <https://9hyeon1225.github.io/LAC/>

### 2) 코드

최종 SUMO 환경과 AV를 재현할 수 있는 코드 제출

가능하면

```text
Environment
Training
Evaluation
Data Collection
```

코드를 구분하여 정리하는 것 권장

팀별로 개인 Github에 코드 업로드 후 깃허브 링크 제출

- 예시 자료 1: <https://github.com/park-sangeun/Multi-Square>
- 예시 자료 2: <https://github.com/9hyeon1225/van>
- 예시 자료 3: <https://github.com/9hyeon1225/LAC>

깃허브 링크는 프로젝트 페이지에 포함 필요

### 3) 발표자료

최종 발표 시 사용한 발표자료 제출

발표자료는 구글 드라이브 등에 올려서 프로젝트 페이지에 포함 필요

### 4) 주행 데이터

프로젝트에서 수집한 주행 데이터를 Hugging Face에 업로드 후 링크 제출

- 제공된 데이터 수집 기본 코드에서 수집하는 데이터 항목은 반드시 포함해야 함
- 구축한 도로 환경에 맞게 추가 항목에 대해 수집하는 것 허용
  - 중간 발표 이후 데이터 칼럼 scope 제한 예정

### 기본 데이터 수집 항목

제공된 `collect_pomdp_data.py`에서는 **POMDP transition 단위**로 데이터를 저장하며, 기본적으로 다음 항목을 포함함

| 항목 | 형태 | 의미 |
|---|---|---|
| `episode` | Integer | Episode 번호 |
| `t` | Integer | Episode 내부 timestep |
| `observation` | Vector (19-dim) | 시점 $t$에서 AV Policy가 실제로 입력받는 부분 관측 $o_t$ |
| `action_raw` | Vector (2-dim) | Policy가 출력한 원본 Action `[가감속, 차선변경]` |
| `action.accel_raw` | Float | 환경에 전달된 가감속 Action 값 |
| `action.lane_change_raw` | Float | 환경에 전달된 차선변경 raw 값 |
| `action.lane_change` | Integer | 실제 명령으로 변환된 차선변경 값 `{-1, 0, +1}` |
| `action.lane_change_applied` | Boolean | 차선변경 명령이 실제 적용되었는지 여부 |
| `reward` | Float | 시점 $t$에서 받은 Reward $r_t$ |
| `terminated` | Boolean | 충돌 / 도착 등 환경 자체의 종료 여부 |
| `truncated` | Boolean | 최대 Episode Step 등 시간 제한에 의한 종료 여부 |
| `state` | Dictionary | SUMO 내부의 privileged simulator state $s_t$ |
| `detected_vehicles` | List | Observation 시점에 감지된 주변 차량 정보 |
| `event.collided` | Boolean | 해당 step에서 충돌 발생 여부 |
| `event.arrived` | Boolean | 목적지 도착 여부 |
| `event.lane_before` | Integer / String | Action 적용 전 AV 차선 |
| `event.lane_after` | Integer / String | Action 적용 후 AV 차선 |
| `next_observation` | Vector (19-dim) | 다음 시점의 부분 관측 $o_{t+1}$ |
| `next_state` | Dictionary | 다음 시점의 privileged simulator state $s_{t+1}$ |

> `next_observation`과 `next_state`는 저장 용량을 줄이기 위해 JSONL 파일에서는 Episode 마지막 step에만 직접 기록하며, 데이터를 읽을 때 다음 transition의 `observation`과 `state`를 이용하여 복원 가능

또한 학습에서 바로 사용하기 쉽도록 `.npz` 파일에는 다음 항목을 별도로 저장함

```text
observation / action_raw / lane_change / reward / next_observation
terminated / truncated / episode / t
detected_xy / detected_offsets
```

> **위 기본 데이터 항목은 반드시 포함해야 하며, 각 팀의 도로 구조와 자율주행 문제에 필요한 추가 State / Observation 항목은 자유롭게 확장 가능**
